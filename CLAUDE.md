# Task Management — Docker Setup Guide

This guide explains how to run the entire project (Spring Boot app + PostgreSQL) using Docker, share the database with collaborators via GitHub, and extend the setup with additional microservices in the future.

---

## Project Structure

```
project-root/
├── Dockerfile                  ← Builds the Spring Boot image
├── docker-compose.yml          ← Orchestrates all containers
├── export-db.sh                ← One-time script: dumps local DB for Docker
├── .env                        ← Your secrets (DO NOT commit — in .gitignore)
├── .env.example                ← Template for secrets (safe to commit)
├── .gitignore
└── docker/
    └── postgres/
        └── init/
            └── 01-dump.sql     ← Generated by export-db.sh (safe to commit)
```

---

## Step 1 — Export Your Existing Database (Run Once)

Before running Docker for the first time, export your local PostgreSQL data:

```bash
chmod +x export-db.sh
./export-db.sh
```

This creates `docker/postgres/init/01-dump.sql`. The PostgreSQL Docker container automatically imports every `.sql` file in that folder on its **first** start (i.e. when the volume is empty).

> **Tip:** Commit `docker/postgres/init/01-dump.sql` to Git. This is how collaborators get a working database when they clone the repo.

---

## Step 2 — Create Your `.env` File

```bash
cp .env.example .env
```

Open `.env` and fill in all real values. This file is listed in `.gitignore` and will never be committed.

---

## Step 3 — Build and Start Everything

```bash
docker compose up --build
```

- PostgreSQL starts first and becomes healthy.
- Spring Boot starts only after the DB is healthy (`depends_on` + `healthcheck`).
- The app is available at **http://localhost:8080**
- The DB is available at **localhost:5432** (for pgAdmin / DBeaver on your host machine).

To run in the background:

```bash
docker compose up --build -d
```

---

## Useful Commands

| Action | Command |
|---|---|
| Start all services | `docker compose up` |
| Stop all services | `docker compose down` |
| Stop and delete the DB volume (full reset) | `docker compose down -v` |
| View logs | `docker compose logs -f` |
| View logs for one service | `docker compose logs -f app` |
| Rebuild only the app | `docker compose up --build app` |
| Open a psql shell in the DB container | `docker compose exec postgres psql -U postgres -d task_manager` |

## How the Containers Talk to Each Other

All containers are connected to a Docker bridge network called **`tasknet`**. Within this network, each container is reachable by its **service name** as a hostname:

```
app  →  postgres:5432   (Spring Boot → PostgreSQL)
```

That is why `application.properties` uses `localhost:5432` locally, but Docker Compose overrides the URL to `jdbc:postgresql://postgres:5432/task_manager` via an environment variable. You do **not** need to change `application.properties`.

## Publishing to GitHub (So Others Can Run It)

Commit these files:

```
✅ Dockerfile
✅ docker-compose.yml
.env.example               ✅ (template, no real secrets)
.gitignore                 ✅
export-db.sh               ✅
docker/postgres/init/01-dump.sql  ✅  ← collaborators get your data
```

Never commit:

```
❌ .env                    ← real secrets
```

Collaborators clone the repo and run:

```bash
cp .env.example .env
# fill in their own API keys
docker compose up --build
```

They get your exact database schema and seed data automatically.

---

## Updating the Database Dump

Whenever you make significant changes to your data that collaborators should also have, re-run:

```bash
./export-db.sh
git add docker/postgres/init/01-dump.sql
git commit -m "chore: update database dump"
git push
```

> **Note:** The dump is only auto-imported when the Docker volume is empty (first run). Existing collaborators must run `docker compose down -v` first to reset their volume, then `docker compose up`.

## Adding a Future Microservice

To add a new service (e.g. a notification service), add a block to `docker-compose.yml`:

```yaml
  notification-service:
    build:
      context: ../notification-service   # path to the other project
      dockerfile: Dockerfile
    container_name: notification-service
    restart: unless-stopped
    environment:
      SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/task_manager
      # ... other env vars
    ports:
      - "8081:8080"
    networks:
      - tasknet          # ← same network = can talk to app and postgres
    depends_on:
      postgres:
        condition: service_healthy
```

Because it shares `tasknet`, it can reach:
- `postgres:5432` — the database
- `app:8080` — the main application
- Any other service by its service name

## Updating `application.properties`

No changes are needed for local development. For Docker, the datasource URL is overridden by the environment variable `SPRING_DATASOURCE_URL` set in `docker-compose.yml`. Spring Boot automatically maps `SPRING_DATASOURCE_URL` → `spring.datasource.url`.

If you want to make it explicit, you can change the line in `application.properties` to:

```properties
spring.datasource.url=${SPRING_DATASOURCE_URL:jdbc:postgresql://localhost:5432/task_manager}
```

This means: use the env var if set, otherwise fall back to `localhost` (for local dev without Docker).
